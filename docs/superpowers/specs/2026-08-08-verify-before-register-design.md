# ยืนยันอีเมลก่อนสร้างบัญชี — ส่วน platform

ดีไซน์ฉบับเต็มอยู่ที่ฝั่ง backend เพราะแกนของงานอยู่ที่นั่น:
`../../../carmen-turborepo-backend-v2/docs/superpowers/specs/2026-08-08-verify-before-register-design.md`
(ข้อ 10 คือส่วนที่ว่าด้วยคำเชิญทั้งหมด)

เอกสารนี้สรุปเฉพาะสิ่งที่เปลี่ยนในรีโปนี้

## ทำไมรีโปนี้ถึงเกี่ยว และเกี่ยวแค่ไหน

เส้นทางสมัครกำลังกลับลำดับเป็น **ยืนยันอีเมล → สร้างบัญชี** ผลพลอยได้คือ token ของคำเชิญ ซึ่งถูกส่งไปยัง
อีเมลของผู้รับอยู่แล้ว **พิสูจน์ความเป็นเจ้าของอีเมลอย่างเดียวกับลิงก์ยืนยัน** ผู้ถูกเชิญที่ยังไม่มีบัญชี
จึงไม่ต้องไปสมัครแยกแล้วยืนยันอีเมลซ้ำอีกรอบ — ตั้งรหัสผ่านแล้วเข้าร่วมได้ในลิงก์ใบเดียว

**ขอบเขตของรีโปนี้คือฝั่งออกคำเชิญเท่านั้น ซึ่งถูกต้องอยู่แล้วและไม่มีหน้าจอใหม่** เพราะคำเชิญออกได้
เฉพาะ Cluster Admin ส่วน **หน้ารับคำเชิญ** (`/invitations/:token`) เป็นของผู้ใช้ปลายทาง จึงไปอยู่ที่
`carmen-inventory-frontend-react` รวมกับหน้าสมัครและหน้าล็อกอินที่ผู้ใช้กลุ่มเดียวกันใช้อยู่แล้ว

สิ่งที่ต้องแก้ที่นี่คือข้อความที่ตามหลัง flow ใหม่ไม่ทัน

## หน้าจอที่ต้องปรับ

| ไฟล์ | สิ่งที่เปลี่ยน |
|---|---|
| `src/pages/clusterAdmin/InviteUserDialog.tsx` | `DialogDescription` บอกได้แล้วว่าผู้รับไม่จำเป็นต้องมีบัญชีมาก่อน คำเชิญพาเขาสมัครให้เอง |
| `src/pages/clusterAdmin/InvitationsTable.tsx` | `accepted` ตอนนี้อาจหมายถึง "สมัครและเข้าร่วมพร้อมกัน" — ตรวจข้อความและ tooltip ให้ไม่ขัด ส่วน `statusVariant` และเงื่อนไข resend/revoke ไม่ต้องแก้ |
| `src/pages/platformConfig/InvitationConfigCard.tsx` | ตรวจว่าไม่มีข้อความที่บอกว่าผู้รับต้องสมัครก่อน |
| `src/services/clusterAdminService.ts` | ไม่ต้องแก้ — endpoint ฝั่ง Admin เหมือนเดิมทั้งหมด |

## สิ่งที่ Admin ควรเห็นเพิ่ม

บัญชีที่เกิดจาก `accept-with-signup` จะถูกบันทึกใน `tb_activity` ว่ามาจากเส้นทางคำเชิญ ไม่ใช่การสมัครเอง
(ข้อ 6 ของดีไซน์ฉบับเต็ม — เป็นกลไกตรวจจับกรณี token คำเชิญหลุด) ถ้าหน้าจอ activity ของรีโปนี้แสดง
เส้นทางที่มาได้ ก็ควรแสดง แต่ไม่ใช่เงื่อนไขของงานนี้

## ลำดับ deploy

**ปล่อยเมื่อไรก็ได้** รีโปนี้เปลี่ยนแค่ข้อความ ไม่พึ่ง endpoint หรือฟิลด์ใหม่จาก backend เลย
